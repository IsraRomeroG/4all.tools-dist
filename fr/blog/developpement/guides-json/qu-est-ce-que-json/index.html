Qu’est-ce que JSON ? Guide pratique de sa syntaxe

Découvrez ce qu’est JSON, comment fonctionne sa syntaxe et pourquoi ce format sert à échanger des données structurées.

L’idée principale

JSON représente des données sous forme de texte selon des règles communes pour que des applications puissent les échanger. Les objets regroupent des paires clé-valeur et les tableaux contiennent des listes ordonnées de valeurs.

{"produit":"Cahier","prix":49.9,"disponible":true}

JSON est un format qui représente des données sous forme de texte, selon des règles communes, pour que des applications puissent les échanger. Son nom signifie JavaScript Object Notation. Bien qu’il provienne de JavaScript, il peut être utilisé avec d’autres langages de programmation. Un texte JSON peut décrire un produit, une liste de commandes ou les réglages d’une application. Il organise l’information ; c’est le logiciel qui lit cette information et décide quoi en faire. La norme ECMA-404 définit cette syntaxe indépendante du langage.

Un exemple simple de JSON

Voici un document JSON complet et valide qui décrit un produit fictif :

{
  "produit": "Cahier",
  "prix": 49.9,
  "disponible": true
}

On peut le lire comme une fiche avec trois étiquettes. Le produit s’appelle « Cahier », son prix vaut 49,9 et il est disponible. Aucune monnaie n’est associée à ce prix dans l’exemple. Dans le JSON, le nombre s’écrit 49.9, avec un point.

Chaque étiquette est une clé, suivie de sa valeur. Dans le premier champ, "produit" est la clé et "Cahier" sa valeur. Les accolades { } regroupent les trois champs dans un objet. Les deux-points : relient chaque clé à sa valeur ; les virgules séparent les champs.

Le texte "Cahier" est entouré de guillemets doubles. Le nombre 49.9 et la valeur true, qui signifie « vrai », n’en ont pas. Cette différence donne une indication sur leur type. Le nom "prix" ne suffit pas à rendre une valeur numérique : c’est sa représentation qui compte. Nous allons voir pourquoi les guillemets peuvent changer le sens des données.

À quoi sert JSON ?

JSON permet à des logiciels de partager des informations structurées. Reprenons notre produit dans trois situations :

  • Échange entre applications. Le logiciel d’une boutique prépare la fiche du cahier en JSON. Une application mobile reçoit ce texte, lit le produit, le prix et la disponibilité, puis les affiche. Cet échange peut passer par une API, une interface par laquelle des programmes communiquent. JSON décrit les données échangées ; il n’assure pas lui-même leur transport.
  • Configuration. Un outil ou une personne écrit des réglages dans un fichier JSON. Au démarrage, l’application les lit pour appliquer, par exemple, une langue ou un nombre d’éléments à afficher. Les noms des réglages sont ceux qu’elle sait reconnaître.
  • Exportation et sauvegarde. Un catalogue génère un fichier JSON contenant ses produits. Un autre logiciel peut ensuite l’importer pour réutiliser les informations, à condition d’en comprendre la structure.

Les applications doivent donc s’accorder sur les noms des champs et leur signification. Dans une véritable API, traduire librement "produit" en un autre nom peut empêcher le logiciel de retrouver la donnée attendue.

Objets, tableaux et six types de données

Ajoutons des couleurs, un vendeur et des remarques à la même fiche. Ce document est lui aussi valide :

{
  "produit": "Cahier",
  "prix": 49.9,
  "disponible": true,
  "couleurs": ["bleu", "noir"],
  "vendeur": {
    "nom": "Ana",
    "ville": "Puebla"
  },
  "remarques": null
}

Les crochets [ ] délimitent un tableau : en JSON, ce terme désigne une liste ordonnée de valeurs. Ici, elle contient deux couleurs, « bleu » puis « noir ». Un tableau n’est donc pas nécessairement une grille de lignes et de colonnes.

Le champ "vendeur" contient un autre objet, avec ses propres accolades. Cette imbrication regroupe le nom et la ville du vendeur au sein de la fiche produit. Les retraits en début de ligne aident à voir cette organisation.

JSON possède six types de données. Le même exemple permet de les reconnaître. JSON.org présente leur structure.

Type Valeur dans notre exemple Comment la lire
Chaîne de caractères "Cahier" Du texte entre guillemets doubles.
Nombre 49.9 Une valeur numérique.
Booléen true Une valeur « vrai » ou « faux » : true ou false.
Tableau ["bleu", "noir"] Une liste dont l’ordre est conservé.
Objet {"nom":"Ana","ville":"Puebla"} Des informations regroupées par clés.
Nul null Une valeur nulle explicitement indiquée.

Dans notre catalogue fictif, "remarques": null signifie qu’aucune remarque n’est enregistrée. C’est une convention du catalogue. null ne signifie pas universellement zéro ou texte vide, et écrire une clé avec null diffère de ne pas écrire cette clé.

Les guillemets changent le type

Les six documents ci-dessous sont complets et valides, mais les deux membres de chaque paire ne représentent pas le même type :

Champ Type d’origine Texte
Prix {"prix":49.9} {"prix":"49.9"}
Disponibilité {"disponible":true} {"disponible":"true"}
Remarques {"remarques":null} {"remarques":"null"}

Dans chaque document de la colonne de droite, la valeur du champ est une chaîne de caractères : des chiffres, le mot « true » ou le mot « null ». Ajouter les guillemets ne rend pas la syntaxe incorrecte ; cela modifie les données que l’application reçoit.

Un document JSON complet peut aussi être un tableau ou une valeur simple, comme 42 ou true. Il ne commence donc pas obligatoirement par une accolade. Le guide JSON de MDN explique également cette possibilité.

Texte JSON, fichier JSON et données d’un programme

Ces trois notions sont liées, mais correspondent à des étapes différentes :

Notion Ce qu’elle désigne
Texte JSON L’information écrite selon les règles du format, comme les exemples ci-dessus.
Fichier .json Un fichier qui conserve ce texte, par exemple produit.json.
Valeur utilisée par un programme Les données obtenues après lecture du texte, que le logiciel peut consulter ou modifier.

Un programme peut recevoir du JSON directement par le réseau, sans ouvrir de fichier .json. Il analyse alors le texte pour obtenir les valeurs qu’il utilisera. Cette opération s’appelle l’analyse syntaxique, ou parsing.

L’opération inverse consiste à représenter des données sous forme de texte JSON : c’est la sérialisation. Il faut ensuite une opération d’écriture pour conserver ce texte dans un fichier. Générer du JSON ne l’enregistre pas automatiquement.

JavaScript possède des fonctions pour effectuer ces conversions, mais JSON reste un format de données, pas un programme JavaScript à exécuter. La syntaxe d’un objet écrit dans du code JavaScript peut d’ailleurs différer de celle d’un document JSON. MDN détaille ces différences.

Enfin, renommer un fichier en ajoutant .json ne convertit pas son contenu. Un texte quelconque peut toujours être incorrect après ce changement de nom.

Les règles de syntaxe et cinq erreurs fréquentes

La syntaxe est l’ensemble des règles d’écriture du format. En JSON, les clés et les chaînes utilisent des guillemets doubles droits ", les champs sont séparés par des virgules, et chaque clé est reliée à sa valeur par deux-points.

Voici cinq documents incorrects, chacun accompagné d’une correction valide :

Erreur Document incorrect Document corrigé
Clé sans guillemets {produit:"Cahier"} {"produit":"Cahier"}
Guillemets simples {'produit':'Cahier'} {"produit":"Cahier"}
Virgule après le dernier champ {"prix":49.9,} {"prix":49.9}
Virgule manquante entre deux champs {"produit":"Cahier" "prix":49.9} {"produit":"Cahier","prix":49.9}
Majuscule dans true {"disponible":True} {"disponible":true}

Les valeurs true, false et null s’écrivent toujours en minuscules, sans traduction. Les commentaires ne font pas partie de JSON standard. Pour les nombres JSON, le séparateur décimal reste le point, même si les clés et les textes sont en français. Les fonctions, undefined, NaN et Infinity ne sont pas des valeurs JSON.

Utilisez aussi des clés distinctes dans chaque objet. Des clés répétées peuvent être traitées différemment selon le logiciel. Pour retrouver une donnée d’un objet, fiez-vous à son nom plutôt qu’à sa position. L’ordre des éléments d’un tableau, lui, est significatif. La RFC 8259 définit ces règles et précautions d’interopérabilité.

Les retours à la ligne et l’indentation — le retrait des lignes — servent à rendre le document lisible. Ils ne remplacent jamais une virgule ou un guillemet manquant.

Si un programme refuse votre document, suivez le guide pour trouver et corriger les erreurs de syntaxe JSON, avec un exemple complet et des corrections minimales.

Ouvrir, modifier et vérifier un fichier JSON

Ouvrir ou créer un fichier

Ouvrez votre fichier dans un éditeur de texte ou de code. Pour commencer sans fichier existant, créez un document texte et copiez le premier exemple à trois champs. Vous n’avez pas besoin d’installer un environnement de programmation.

Après une modification, vérifiez la syntaxe avec un outil de validation JSON standard. Enregistrez ensuite le document comme texte en UTF-8, sous le nom produit.json. Vérifiez que l’éditeur n’a pas ajouté une extension supplémentaire, comme .json.txt. UTF-8 est l’encodage prévu par la norme pour les échanges JSON entre systèmes ouverts.

Distinguer formatage et validation

Un résultat « valide » doit être interprété selon ce que l’outil a réellement vérifié :

Opération Question à laquelle elle répond
Formater Peut-on améliorer la lisibilité avec des retraits et des retours à la ligne ?
Valider la syntaxe Le texte respecte-t-il les règles de JSON ?
Valider avec un schéma Les données respectent-elles les contraintes déclarées pour cette application ?

Un schéma peut préciser qu’un prix doit être numérique ou qu’un champ est obligatoire. Ce contrôle est distinct de la syntaxe. Il ne prouve pas non plus que le prix est exact dans la réalité. L’introduction à JSON Schema explique ce rôle des contraintes.

Une réparation, lorsqu’un outil la propose, modifie l’entrée : il faut vérifier les changements. Elle ne se limite pas nécessairement à sa présentation.

Un exercice pour comprendre « valide »

Partez du premier exemple et appliquez les changements dans cet ordre :

  1. Validez le document initial. Sa syntaxe est valide.
  2. Ajoutez une virgule juste après le dernier true, avant l’accolade fermante. La syntaxe devient invalide : cette virgule annonce un champ qui n’existe pas.
  3. Retirez cette virgule. La syntaxe redevient valide.
  4. Entourez seulement le prix de guillemets doubles. La syntaxe reste valide, mais le prix est maintenant du texte.

Le résultat de la quatrième étape est ce document JSON valide :

{
  "produit": "Cahier",
  "prix": "49.9",
  "disponible": true
}

Supposons que notre catalogue exige un prix numérique. Ce document ne respecte plus cette exigence, bien qu’un contrôle de syntaxe l’accepte. Un validateur vérifiant aussi le schéma correspondant pourrait signaler le mauvais type.

Pour terminer, remettez 49.9 sans guillemets, validez et enregistrez le fichier. Les messages d’erreur peuvent varier d’un outil à l’autre ; c’est le résultat de chaque modification qu’il faut observer.

Facultatif : utiliser JSON en JavaScript

Ce bloc est du JavaScript, pas du JSON. Il reprend la fiche initiale, affiche le nom du produit, remplace le prix et génère un nouveau texte :

const texteJson = '{"produit":"Cahier","prix":49.9,"disponible":true}';
const donnees = JSON.parse(texteJson);

console.log(donnees.produit); // Cahier
donnees.prix = 59.9;

const texteActualise = JSON.stringify(donnees, null, 2);
console.log(texteActualise);

La première sortie est Cahier. La seconde est ce texte JSON, avec un retrait de deux espaces :

{
  "produit": "Cahier",
  "prix": 59.9,
  "disponible": true
}

JSON.parse() interprète le texte. Ici, il produit un objet ; avec un autre document, il pourrait produire un tableau ou une valeur simple. JSON.stringify() génère du texte JSON pour les valeurs compatibles, avec des limites selon les données fournies. Le dernier argument 2 définit le retrait.

Les guillemets simples extérieurs de la première ligne appartiennent à JavaScript : ils délimitent la chaîne contenant le JSON. Ils ne font pas partie du document JSON. Le commentaire après // appartient lui aussi au code JavaScript.

Ce programme affiche le nouveau texte ; il ne l’écrit pas dans un fichier.

Facultatif : JSON, CSV ou XML ?

Ces formats organisent l’information de manières différentes. Le choix dépend des données à représenter et de ce que les logiciels concernés peuvent lire.

Format Organisation et usage adapté
JSON Objets et listes imbriqués, comme notre produit avec plusieurs couleurs et un vendeur.
CSV Enregistrements en lignes et champs séparés, utiles pour des données tabulaires simples.
XML Éléments et attributs délimités par des balises, permettant de structurer des données ou des documents.

Un catalogue plat peut convenir au CSV ; des listes à l’intérieur de chaque fiche se représentent directement en JSON. XML répond à d’autres besoins de structure et de balisage. Aucun n’est le meilleur choix dans tous les cas. Voir la RFC consacrée au CSV et la spécification XML du W3C.

À vous de pratiquer

Reprenez produit.json, changez le nom du cahier et vérifiez sa syntaxe. Avant d’enregistrer, expliquez ce que chaque valeur représente et pourquoi son type convient.

Si vous travaillez avec une API et devez examiner deux versions de sa réponse, consultez le guide pour comparer les réponses JSON d’une API.
