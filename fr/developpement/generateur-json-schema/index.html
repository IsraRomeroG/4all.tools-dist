Générez JSON Schema depuis des documents JSON complets

Déduisez un schéma commun depuis un à vingt exemples JSON, choisissez les champs obligatoires et vérifiez chaque document complet localement.

Espace de travail de l’outil

Générateur de JSON Schema

Activez JavaScript pour déduire un schéma localement dans votre navigateur.

Chaque éditeur contient un document JSON complet. Un tableau à la racine reste un tableau. Les exemples orientent le schéma ; ils ne prouvent pas les règles de votre domaine.

Jusqu’à 20 exemples ; 250 000 unités UTF-16 par exemple et 500 000 au total ; 1 000 000 octets par fichier ; profondeur 20 ; 50 000 nœuds source au total ; 2 000 nœuds déduits ; schéma de 100 000 unités UTF-16 au maximum. Les budgets de travail peuvent être atteints avant.

Le traitement reste dans votre navigateur. Les exemples ne sont ni envoyés ni enregistrés.

        Analysez les documents avant de générer

        Collez un document JSON complet dans chaque éditeur ou ouvrez un fichier local .json UTF-8. Ajoutez jusqu’à vingt exemples indépendants. Sélectionnez Analyser les exemples, examinez les champs déduits puis Générer le schéma. Ces actions sont explicites : charger un exemple ne génère aucun résultat. Tous les exemples doivent être du JSON strict valide. Les éditeurs vides, clés décodées répétées, commentaires, JSONC/JSON5 et nombres perdant de la précision arrêtent toute l’opération. Aucun exemple en erreur n’est écarté.

        Un éditeur contenant un tableau représente un seul document tableau. Tous ses éléments contribuent, y compris les derniers ; ils ne deviennent pas des exemples indépendants. Plusieurs éditeurs produisent un schéma commun à leurs racines. Chaînes, nombres, booléens et null peuvent également être des racines.

        Exemple de tableau :

        [{"id":1},{"id":2,"nombre":"Ana"}]

        Avec les champs obligatoires déduits, le tableau complet satisfait ce schéma :

        {
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "array",
  "items": {
    "type": "object",
    "properties": {
      "id": {
        "type": "integer"
      },
      "nombre": {
        "type": "string"
      }
    },
    "required": [
      "id"
    ],
    "additionalProperties": true
  }
}

        Présence, null et champs obligatoires manuels

        id apparaît dans 2/2 objets et est obligatoire par défaut ; nombre apparaît dans 1/2 et est facultatif. Exiger nombre produit le premier échec à l’instance /0, keyword required, schéma /items/required, propriété absente nombre. Le schéma reste exportable avec un avertissement visible indiquant qu’il n’accepte pas tous les exemples. Chaque document complet est vérifié, avec un premier échec par exemple incompatible. Rétablir les champs obligatoires déduits supprime tous les choix manuels, y compris ceux des autres pages.

        Pour [ {"x":null}, {"x":"a"}, {} ], x est présent dans 2/3 objets, a les types null/string et reste facultatif. Sans l’objet vide, x est obligatoire et reste nullable. L’absence affecte la présence ; null affecte le type. Dans un objet imbriqué, le dénominateur ne comprend que les objets observés à cet emplacement. Une observation montre une présence, pas une obligation du domaine.

        [] génère type: "array" avec items: {} : aucun type d’élément n’a été observé, les éléments sont donc sans restriction. {} ne révèle aucune propriété. Entiers et fractions sont combinés en number ; les autres types mixtes utilisent une union type. Les branches objet et tableau sont combinées inline sans déduire relations ni discriminateurs. Le schéma peut ainsi accepter des combinaisons absentes des exemples.

        Draft fixe et suggestions conservatrices

        L’URI fixe est http://json-schema.org/draft-07/schema#. Le vocabulaire émis comprend $schema, type, properties, required, items, additionalProperties et les annotations facultatives title/description à la racine. Les objets restent ouverts avec additionalProperties: true. Aucun sélecteur de draft ni déduction de règles de format, enums, intervalles, motifs, références, tuples ou anyOf/oneOf/allOf n’est proposé.

        Activez les suggestions avant l’analyse pour voir des candidats conservateurs d’e-mail ASCII, URI HTTP(S) absolue et date grégorienne valide YYYY-MM-DD. Au moins deux chaînes doivent satisfaire le même détecteur ; un contre-exemple ou une chaîne de plus de 1 024 unités UTF-16 élimine le candidat. Les exemples identiques comptent comme observations, sans prouver une évidence indépendante du domaine. Ce sont des métadonnées visibles : format n’est ni émis ni vérifié par le validateur actuel. Copiez le schéma et collez-le manuellement dans le validateur associé ; les liens ne transfèrent aucune donnée.

        Limites, exports complets et confidentialité

        L’entrée originale permet 250 000 unités UTF-16 par exemple, 500 000 au total et 1 000 000 octets par fichier. Chaque exemple permet une profondeur de 20 et 25 000 nœuds source ; l’ensemble permet 50 000 nœuds. Le modèle permet 2 000 nœuds déduits et 2 000 propriétés, avec une profondeur logique de 20. L’analyse dispose de 1 000 000 unités de travail par document ; la précision de 1 000 000 partagées ; la déduction et la validation de 5 000 000 partagées chacune. Tous les maxima ne peuvent pas forcément être atteints simultanément.

        Le schéma complet permet 100 000 unités UTF-16, 5 000 nœuds JSON et une profondeur JSON d’analyse de 60. La normalisation conserve une profondeur sémantique de 40, 5 000 visites et 5 000 noms. Le titre permet 256 unités et la description 2 000 ; l’indentation utilise deux ou quatre espaces. Les chemins permettent 2 048 unités ; jusqu’à vingt diagnostics et 8 192 unités de texte diagnostic sont publiés. Chaque page permet vingt-cinq entrées et 20 000 unités de texte, avec 8 192 par entrée. Une entrée trop longue fait échouer toute l’analyse. L’analyse et la génération expirent après 8 secondes ; les pages après 2 secondes. Limites, annulations et erreurs opérationnelles ne publient ni schéma ni vérification partielle.

        Les fichiers utilisent UTF-8 strict. Un BOM initial est retiré avec un avertissement et les coordonnées restent relatives à l’original visible ; un second BOM initial est invalide. Modifier un exemple, commencer une lecture, relancer l’analyse ou changer les suggestions invalide le snapshot et les champs obligatoires choisis. Changer les champs obligatoires ou les options invalide la sortie. Annuler termine le Worker ; relancez l’analyse pour continuer.

        La copie et le téléchargement exportent le même schéma complet actuel, quelle que soit la page de champs. Le téléchargement utilise schema.json, application/schema+json, UTF-8 sans BOM, LF et aucune fin de ligne finale. En cas d’échec du presse-papiers, copiez manuellement la sortie complète en lecture seule. Le traitement est local, sans envoi, URL distante, télémétrie ni stockage du contenu. JavaScript et un navigateur compatible avec Worker sont nécessaires.
